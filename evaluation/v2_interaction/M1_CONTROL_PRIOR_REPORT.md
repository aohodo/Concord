# Concord V2 M1 控制先验阶段报告

更新日期：2026-09-28

## 结论

当前 M1 能独立完成 Shared Problem Formulation，并在条件满足时输出保留不确定性的 `ResolutionContext`。实现原则是：

> Human behavior provides computational priors for Agent control.

人类行为先验在这里控制注意、思考、停止、扩大搜索和经验复用，不承担拟人化表演。用户状态由模型结合整句和会话上下文做语义解释；代码负责证据引用、状态约束、问题预算、重复失败保护和 `CASE_READY` 边界，不用“15 分钟/一刻钟/着急”等关键词表枚举表达。

## 已验证能力

- 目标、观察、行动、行动结果和假设分开保存，`reported` 不等于 `verified`。
- 关键证据缺失、矛盾未解决或共同目标未形成时不能进入 M2。
- 用户无法提供的证据可标记为 unavailable，应该由后续阶段获取的证据可 deferred。
- 失败动作进入 ledger；系统可持续保留“不要无条件重复”的控制先验。
- 急迫、低耐心、低控制感等语义状态会改变问题预算、回复长度和下一步负担，而不只改变措辞。
- 默认行为策略是编译式控制；只有实质矛盾才增加一次模型审议调用。
- 240 个 Episode 规格覆盖 30 个问题场景 × 8 个交互条件，交互条件不是永久人口画像。

## 对“客服场景可以宽一点”的处理

M1 不要求用户首轮给出专业、完整的问题陈述，也不把澄清轮数本身当失败。客户可能只给一句现象、一张截图或错误地猜原因。M1 的硬要求仅是：

- 不扭曲用户目标；
- 不把猜测升级为事实；
- 不遗漏会改变处置路径的关键约束；
- 不在证据不足时伪造 `CASE_READY`。

产品级成功必须在 M2/M3 继续测量：最终解决率、首个有效动作时间、总耗时、重复失败动作、用户操作负担、升级是否合理，以及用户对结果的确认。`resolution_success` 在 M1 评测中固定为 `unavailable`，避免用“问题表征完成”冒充“问题已解决”。

## 尚未解决

1. 真实模型时延过高。当前代表性完整 Case 为 136–150 秒，不符合实时支持产品体验。
2. 用户纠正旧假设的在线稳定性不足。结构化 schema 和证据覆盖校验仍需继续收敛。
3. 当前 240 个 Episode 是丰富的合成压力集，不是真实客服日志，也不能替代最终任务解决评测。
4. 尚未完整运行 240 个在线 Episode；受调用成本约束，目前只做了代表性验证。
5. 图片证据已验证模型能力和适配层，但尚未正式进入 M1 的带来源证据模型。

## 下一步边界

- M1：继续修复语义纠错稳定性和媒体证据 provenance，不加入关键词分类器。
- M2：以 `ResolutionContext` 为输入，测量闭环诊断和最终任务结果。
- 产品总评：以解决结果为主，M1 的事实忠实度和安全边界为必要条件，而非唯一成绩。
